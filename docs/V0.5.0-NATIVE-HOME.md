## Mechanism and exact unresolved interface

The two controls query default handling of `http://tizen.org/appcontrol/operation/main` using a bundle and `aul_get_default_app`; they assign it using `app_operation_set_current_app` and write `db/appfw/home_appid` with vconf. They separately query `util_is_appbooting_supported_webapp_byappid`. CleanFrame additionally enables autostart; that write is outside this task's Home-only scope. These are mechanisms demonstrated on the references' firmware, **not a confirmed map of the physical Home event on 2743.0**.

The missing interface is a **permitted native execution/read/write route to those calls, with actual ABI, execution identity and permissions verified on T-KSU2FUABC-2743.0**. Ordinary SDK app launching is not that interface. The historical capability `netcoredbg_support:enabled` does not establish a runtime, arbitrary execution permission, native exports or access as UID 901.

## Implemented changes

- [`compatibility.mjs`](../scripts/native-home/compatibility.mjs): an offline command that hashes the actual SDK/evidence inputs, lists the application API surface, retains historical evidence dates, records every native value as unread and returns specific blockers. It contains no process, network, SDB or staging transport. Missing local evidence produces an unavailable result; malformed or mismatched historical device records are refused. Imported JSON claims cannot enable execution.
- [`cli.mjs`](../scripts/native-home/cli.mjs): adds the offline `compatibility` command. Existing `apply` and `restore` commands still reject before any TV operation, including with force/approval-like arguments. `inspect` remains the older capabilities-only SDB command and was not run.
- [`recovery.mjs`](../scripts/native-home/recovery.mjs): compares every native field against the expected state before each simulated restoration step, rechecks after intent persistence, and rejects cross-field side effects or a previously restored field changing back. An unverified eligibility record must contain null, not a guessed boolean.
- [`compatibility.test.mjs`](../scripts/native-home/compatibility.test.mjs) and [`recovery.test.mjs`](../scripts/native-home/recovery.test.mjs): exercise SDK absence/malformed data, exact target guards, forged compatibility claims, offline filesystem integration, production CLI rejection, partial changes, lost connectivity, journal failure, readback mismatch, missing FrameOS, changed firmware/fingerprint and concurrent state drift.
- [`physical-test-record.example.json`](../scripts/native-home/physical-test-record.example.json): an explicitly unrun record for the separately approved native experiment and restoration test.
- `package.json`: adds `npm run test:native-home`. No controller implementation, application source, native privilege, manifest, certificate, signing profile or startup setting changed.

## Recovery capability and limits

The existing baseline tooling preserves typed values, binds exact identity/fingerprint/firmware, uses exclusive file creation and SHA-256 envelopes, and reads back two distinct off-TV copies. It refuses unknown values, mock production baselines, mismatched/corrupt copies, links, unexpected drift and firmware mismatch. A second copy on another physical disk and an offline copy are still recommended. Checksums detect corruption, not fabricated provenance.

The strengthened restore engine is **mock-only**. It requires no FrameOS process/package in its tests, but there is no native transport to exercise on the TV. It restores only understood Home-operation/Home-ID differences, never silently overwrites unexpected startup changes. Recovery from firmware-specific derived startup changes remains unresolved. A timed-out write has an uncertain result and must not be replayed; a fresh independent query would be required.

Therefore there is no honest executable apply or restoration command to approve now. The original values, permitted transport and physical independent recovery evidence are missing. No package or helper was staged to test a hypothetical access path.

## Physical protocol after the missing interface is established

This protocol is prepared but **not executed**. It does not authorize staging, writes or power operations.

1. Establish Samsung-authorized access to the required native reads and restoration on this firmware. Verify the actual runtime/ABI, UID, stable device identity and device-read firmware. Any temporary helper staging or special permissions need a separate proposal stating files, signatures, privileges, execution identity, commands, output and cleanup; obtain explicit approval before execution.
2. Run the dedicated read-only query without setters or app launches. Capture all six typed fields, boot eligibility and raw native statuses. Refuse missing/ambiguous/unsupported reads. Save the genuine original baseline to two independently readback-verified off-TV locations, plus an offline copy. Do not overwrite originals with an applied state.
3. Prepare an independent restore implementation bound to those originals. With separate approval, validate its route while FrameOS is closed, including exact readback. Writing even the existing value is a native write. Disclose that a same-value test alone does not prove recovery from a partially changed configuration.
4. Present the exact original main owner/Home ID, compatibility/eligibility evidence, minimum justified Home-only changes, unchanged startup fields, apply/restore commands and recovery limitations. Obtain explicit approval for that specific one-shot change with the owner watching. Do not infer that both reference writes are needed on this firmware.
5. Confirm the installed FrameOS app works, the explicit Samsung Home escape works, and independent restoration is available. Query the exact current baseline again. Apply once with complete current-state preconditions and immediate typed readback of every field. Do not change autostart, startup, boot backup, first-screen, native Art, Power, Settings or installed Samsung Home.
6. On any failed/mismatched write, stop further assignment attempts, query independently and use only the previously validated recovery procedure within its approval. Record both failures if restoration fails or is uncertain. Never retry blindly, uninstall, reboot or improvise an alternate transport.
7. Following successful readback, open Samsung Home and have the owner physically press Home. Then open one verified installed streaming app and press physical Home again. Record the actual screen, native/API output, elapsed time and unexpected behavior separately. Native write success alone is not a pass.
8. Obtain separate approval for restoration. Restore exact saved originals, read all fields back, and have the owner press Home to confirm Samsung Home. Verify FrameOS remains an ordinary installed app and Settings/Sources still work. Only after that physical restoration may a separate reapply be considered.
9. After Home and recovery work, cover Netflix, YouTube, another app, Samsung Home, FrameOS escape, HDMI, All Apps, Media Hub, internal Art, FrameOS Settings and native TV Settings. Keep native Art, startup, installation retention and Home persistence as separate results. Standby/power-cycle/startup changes require their own approval; none is part of this run.

Use the example record without replacing unknowns with reference values. Until these gates can be met, Home routing stays unchanged; its exact native owner has not been read.
