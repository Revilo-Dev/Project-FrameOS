## Implemented behavior

- Bottom-centred Back / Play-Pause / Next controls, top title gradient, 9 px timeline with a circular knob and subtle knob focus. Progress updates once per second with CSS interpolation. Other controls retain visible focus. Overlays hide after four seconds while playing; OK immediately pauses a hidden player.
- ChannelUp / ChannelDown use codes returned by `getSupportedKeys()`, registered only for the player. They skip 30,000 ms through the existing single-owner AVPlay operation gate. Repeats during a seek are discarded. Samsung excludes exact seek endpoints, so targets are clamped to 1 ms through duration minus 1,000 ms. Paused playback stays paused. Desktop PageUp / PageDown and Space provide testing fallbacks; timeline arrows retain 10-second seeking.
- Autoplay Next Episode defaults ON and persists under the existing media-preference key. Natural completion offers a 1.6-second cancellable transition. Back cancels it and leaves Replay available. Manual stop, Back, paused completion and errors in a manually selected video do not autoplay. Automatic candidates that are missing or fail preparation are skipped in order, with no wraparound. Episode/season metadata is preferred within the series; otherwise names sort naturally. Hidden entries are excluded unless Show Hidden Files is ON. Native audio/subtitle language selections are restored where compatible tracks and APIs exist.
- Continuous vertical scrolling uses fixed row geometry and a five-row render window, plus at most one focused off-window card during movement. At 1080p, six approximately 277 px cards fit per row; the narrower existing layout uses four. Focus scrolls fully into view. No pages or Next Page controls are used.
- Root storage discovery and cached-library restoration start in the background on launch without moving Home focus. Only the first connected drive's root is enumerated at startup. Other drives/folders are enumerated when selected. Refresh and lifecycle restoration reconcile the current folder. USB watching also detects changes while Home is visible.
- Recoverable timeout/inaccessible errors show exactly **Home hub is updating try again soon**, with a focusable **Refresh** button. Refresh is deduplicated. Permission/unsupported errors, initial loading, refreshing, empty folders and disconnected storage remain distinct internally. Removal clears playable UI entries immediately; disconnected storage retains **Connect a USB device**.
- Settings → Media contains Autoplay Next Episode and Clear Media Cache. Clearing disposable caches retains hidden-file preferences and other settings.

## Thumbnail capability and fallback order

1. An existing cached snapshot or reference, keyed by drive, path, size and modification time.
2. Samsung's Content API: exact URI lookup of an already-indexed Content object. Existing thumbnail URIs are used when loadable; otherwise `createThumbnail()` is tried if exposed. That documented public API requires `content.write`, added only to the fresh v0.4 packaging copy. No content scanning, metadata updates or source-video writes are performed. Platform-generated thumbnails choose their own frame and size. Missing/unindexed USB videos fall through.
3. Capability-tested HTML video decoding and canvas capture at 15 seconds, or 20% of a short file, encoded to a 320×180 JPEG. Invalid sources, unsupported MIME types, errors/timeouts, blank readback and tainted canvases fall through. An AVPlay object is never drawn into canvas.
4. A same-basename `.jpg` sidecar, then a bounded `.frameos-thumbnails.json` manifest containing FFmpeg snapshot references. References and images must resolve through read-only Tizen file APIs and load successfully. Paths cannot escape the current directory.
5. The existing placeholder.

One extraction runs at a time, with a bounded 36-job queue for the visible/near-visible cards. Playback pauses extraction and aborts HTML decoding. USB removal aborts/invalidates outstanding results. Native callbacks retain their slot until completion/timeout. Successful results live for 24 hours; unsupported outcomes for five minutes. An invalid cached image gets one retry through the provider.

**Physical-TV extraction is unverified.** Unit tests exercise native creation, HTML frame capture through controlled video/canvas doubles, failures, persistence and eviction. Browser tests exercise real local image loading and the native-index/fallback contracts through fixtures; these do not establish native decoding or screenshot support on the QA32LS03TBWXXY. FFmpeg/FFprobe were not present on this PC's PATH, so the PC generator was tested using a simulated subprocess fixture, not a real media decode.

The optional PC workflow does not run automatically:

```powershell
# Install FFmpeg/FFprobe separately and make them available on PATH.
node scripts/generate-thumbnails.mjs 'D:\PC-Media\Series'
# Optional explicit traversal:
node scripts/generate-thumbnails.mjs 'D:\PC-Media' --recursive
```

Run against a PC copy of the media. Copy each `.frameos-thumbnails.json` and its `.frameos-thumbnails` folder beside the unchanged matching videos on USB, preserving their modification times where possible. The tool skips unchanged images and never rewrites videos. A manifest is capped at 256 KiB. The TV never reads an entire video into JavaScript memory or transcodes MKV.

## Cache schema and limits

IndexedDB schema version 1 uses private-app databases `frameos.media.v4.directories` and `frameos.media.v4.thumbnails`. Directory records include schema, drive identity, relative directory, exact filenames/paths, display labels, types/extensions, size/mtime, native hidden state, episode/season metadata and thumbnail cache keys. User-hidden identities remain separately in the existing small preference record and are applied when displaying cached entries.

Directory storage is capped at **128 directories / 8 MiB** of estimated serialized UTF-16 payload. Thumbnail storage is capped at **256 records / 8 MiB**, with **128** in the immediate memory LRU. IndexedDB bookkeeping overhead is additional. Oversized directory records are browsable but not persisted. Invalid records are ignored; denied, blocked, stalled, corrupt or full IndexedDB degrades to a bounded in-memory cache. No bulk media metadata or bitmap data is put into localStorage. LRU writes are serialized.

The Samsung-generated native thumbnails are platform-owned files; these app limits govern stored app snapshots and references, not Samsung's own media-index cache. Clear Media Cache does not delete Samsung's index or USB files. Mount labels/root paths are the stable identity exposed by this read-only TV filesystem API; it exposes no USB hardware UUID here. A replacement drive reusing a label can briefly show old cached metadata until reconciliation. Every video is re-resolved on the connected drive before AVPlay opens it.

Refresh replaces deleted/renamed/stale entries and updates changed size/mtime keys. Removal rejects late native callbacks. Cached disconnected entries are not exposed for playback. Corrupt directory paths cannot be restored. No recursive startup scan or app-managed USB cache writes occur; Samsung chooses storage for its native thumbnails.

## Startup feasibility

Samsung documents **Settings → General → Smart Features → Autorun Last App** for 2017–2021 televisions, and states app support varies. This establishes the relevant 2020 menu, not eligibility of a developer-installed FrameOS package. That eligibility remains **unknown until tested on this TV**. See [Samsung's official support article](https://www.samsung.com/au/support/tv-audio-video/use-autorun-start-screen-options-on-your-samsung-tv/).

FrameOS now revalidates its retained directory on `visibilitychange`/`pageshow`, keeps screen/folder/filter/hidden preferences in the running app, and closes native video when hidden or on `pagehide`. It restores browsing without resuming playback unexpectedly. A cold relaunch returns to Home while warming connected root metadata. No documented ordinary TV-web-app boot receiver or system-launcher replacement was established; no boot metadata, foreground polling or launch/restore app-control metadata was added. OS-delivered resume is separate from power-on launch. See [Samsung's lifecycle guidance](https://developer.samsung.com/smarttv/develop/getting-started/quick-start-guide.html).

Safe physical test, after an approved installation:

1. Record the existing Autorun Last App setting and Art Mode behavior. Enable the normal setting manually if desired.
2. Open FrameOS, leave it as the last active app, power off normally, then wake. Record whether it restores Home, the running folder, or Samsung Home.
3. Repeat normal standby/wake three times. Test a separate full cold boot/power cycle and record it separately; standby does not establish cold-boot startup.
4. Use YouTube, Stan or Foxtel before shutdown. Confirm FrameOS does not take over that app on wake.
5. Enter/exit Art Mode, including its normal short-power-button behavior. Confirm FrameOS does not interrupt it.
6. Test background/resume with USB removed and reinserted, and verify the folder refreshes without automatically playing video.

If native startup is ineligible, an **optional external controller is only a design option**. It would require separate approval and setup, a genuine off→on/wake event, one launch maximum per wake, at most two bounded connection retries, and positive evidence that FrameOS was the user's intended last app. If active-app or Art Mode status is unknown, it must do nothing. SDB availability alone cannot distinguish a wake from an app change. The existing SDK `tizen run -s 192.168.0.23:26101 -p TdjFk7yyVS.frameos` could be the explicitly gated launch action; no controller, scheduled task or loop has been implemented or enabled.
